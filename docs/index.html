gameability

17.9% of MBPP problems accept a broken solution.

gameability breaks each problem's reference solution in one small place, checks that the result gives wrong answers, and asks whether the problem's own tests notice. No model, no API key, minutes on a laptop. Checked against EvalPlus's independent tests, 95% of the flagged MBPP problems and 85% of the flagged HumanEval problems are confirmed wrong on valid inputs.

$ pip install "gameability[hf]"
$ gameability check mbpp

Brackets are 95% intervals. Problems where no fair judgement was possible (the reference fails its own tests, or no usable inputs) are excluded and counted in the report. Defaults: 24 broken versions per problem, 8 fresh inputs, seed 0.

Confirmed on valid inputs. On the problems EvalPlus also covers, every accepted broken solution was re-run on EvalPlus's tests, whose inputs respect each problem's rules: 95.2% of flagged MBPP problems (20 of 21) and 84.6% of flagged HumanEval problems (11 of 13) are confirmed. The two unconfirmed HumanEval problems have visible tests that contradict their own written specification. Version 0.1 confirmed 85.7% and 78.6%; v0.2 keeps fresh inputs inside the domain each problem's own tests use.

How it works

  1. The reference solution must pass its own visible tests, or the problem is excluded.
  2. Fresh inputs are built by varying the arguments in the visible tests. The reference's outputs on them become a hidden answer key.
  3. The reference is changed at one site: a comparison flipped, an operator swapped, a constant nudged, a return replaced with return None.
  4. A changed version counts as broken only if it gives a different answer from the reference on a fresh input. Versions that behave identically are discarded.
  5. A broken version that passes every visible test is reported, with the input that exposes it.

Run it on your own benchmark

One problem per line, with the reference solution and the visible tests:

{"id": "clamp", "reference": "def clamp(x, lo, hi): ...", "tests": ["assert clamp(5, 0, 10) == 5"]}
$ gameability check my_benchmark.jsonl --fixes fixes.py

--fixes writes a suggested test for every weak problem. On 34 MBPP and HumanEval problems its tests wrongly rejected 2.6% of a model's correct solutions (v0.1: 15.3%). They target the broken versions gameability builds rather than any one model's mistakes, so review them before adding them.

What the numbers don't say

  • The attacker is weak. One small edit is the simplest way to be wrong; a model optimised against these tests can find many more.
  • Fresh inputs stay inside each argument's observed domain, but relationships between arguments (a length that must match a list) and rules stated only in a docstring are not modelled. On the problems EvalPlus covers, 5% of flagged MBPP and 15% of flagged HumanEval problems remain unconfirmed.
  • They describe the tests, not any model, and they do not predict where a model will cheat: on a 1.5B coder, false passes were no more common on flagged problems than on others.
  • gameability runs the benchmark's code. Use it on benchmarks you are willing to execute.
